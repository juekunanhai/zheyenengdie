# 视觉交付流程

依据用户 2026-09-13 的明确要求：“问我之前，先自己跟 UI 对比……自己确定没问题了，再让我审核。”此流程从 R10 自查开始适用于后续视觉批次。

1. 找到对应页面的原 UI，并列出用户后续已确认的变更和 SPEC 排除项。不能用当前实现反过来作为还原标准。
2. 在改动前说明最小方案，以及是否需要更复杂方案；有既有授权的修正继续执行，不重复索取授权。
3. 自行打开原图和当前真实渲染，按相同可见宽度并排比较。至少检查短屏、长屏以及本批次涉及的状态；候选图、浏览器合成、Cocos 运行和真机分别记录。
4. 检查字形与文案、构图间距、配色材质、透明边缘与清晰度、背景层次和动效。重要局部放大比较。图片加载、语法或构建通过不能替代视觉审查。
5. 对重大或可修正的明显差异，先修正、重新截图、再与原图比较。增加独立对抗式复查；不能以“更有质感”为由忽略原 UI 的构图和风格。
6. 自查没有未处理的 P0/P1/P2 差异后，再提交用户审核。已认可的差异与排除功能必须明确记录，不能偷偷把缺陷改称“设计选择”。有未解决问题时如实汇报，不让用户承担第一轮找问题。
7. 用户认可候选后，按获授权的批次接入工程；接入后再次用实际引擎画面对照。候选通过不代表引擎通过，也不自动开始下一玩法批次。

本流程只增加证据和交付门槛，不增加运行时框架、状态、配置或工具依赖。最新批次结论见工程根目录 `design-qa.md`。
